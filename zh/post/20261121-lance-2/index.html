在上篇文章中，分析Lance中的各类文件组织、作用，本篇详细分析其中的数据文件结构（也就是.lance后缀的文件），通过分析其结构，最后我们和Parquet做一个对比。

文件结构 #

如下图所示，一个数据文件通常分为以下几大部分：

  • 存放列数据的数据页面
  • Global Buffer，简称为GBO
  • 存储列元数据的Column Metadata数组
  • Column Metadata Offset Table，简称为CMO，用于存储Column Metadata数组的偏移量
  • Global Buffers Offset Table，简称为GBO，用于存储Global Buffers的偏移量
  • 最后部分是固定长度的Footer
┌──────────────────────────────────────────┐
│ Data Pages                               │  ← 数据
│   Data Buffer 0*                         │
│   ...                                    │
│   Data Buffer BN*                        │
├──────────────────────────────────────────┤
│ Global Buffer 0: schema (protobuf)       │  ← GBO[0]，变长
├──────────────────────────────────────────┤◀── column_meta_start
│ Column Metadatas                         │  ← 每列一个独立 protobuf
│   Column 0 Metadata                      │
│   ...                                    │
│   Column CN Metadata                     │
├──────────────────────────────────────────┤◀── column_meta_offsets_start
│ Column Metadata Offset Table (CMO)       │  ← 16B × CN
├──────────────────────────────────────────┤◀── global_buff_offsets_start
│ Global Buffers Offset Table (GBO)        │  ← 16B × GN
├──────────────────────────────────────────┤◀── file_len - 40
│ Footer (fixed 40 bytes)                  │
│   u64: column_meta_start                 │
│   u64: column_meta_offsets_start         │
│   u64: global_buff_offsets_start         │
│   u32: number of global buffers          │
│   u32: number of columns                 │
│   u16: major version                     │
│   u16: minor version                     │
│   "LANC"                                 │
└──────────────────────────────────────────┘

以下对这几部分进行解释。

数据页面 #

从文件偏移0开始，是多个数据页面，每个页面按照64B进行对齐：

文件偏移 0
┌──────────────────────────────────────────┐
│ page 0 ─ buffer 0   [64B 对齐]            │
│          buffer 1   [64B 对齐]            │ 
│          ...                             │
│ page 1 ─ ...                             │
│                                          │
└──────────────────────────────────────────┘

数据页面存放具体的列数据，但是根据列的不同宽度有不同的布局格式，在后面数据页面布局格式中再进行解释。

Global Buffers #

Global Buffers 保存的是不属于任何页、不属于任何列的“文件级”辅助数据。它只有一条硬规则：

  • GBO[0] 恒为 FileDescriptor（schema + 行数）
  • GBO[1..] 是任意字节，语义靠 Schema.metadata 的 key → “index[:参数]” 引用

GBO 表里每项 16 字节： GBO[i] = (GlobalBuffer[i].position, GlobalBuffer[i].size)

GBO（16B × num_global_buffers）
┌────────────────────┬────────────────────┐
│ position u64       │ size u64           │ → index 0
├────────────────────┼────────────────────┤
│ position u64       │ size u64           │ → index 1
├────────────────────┼────────────────────┤
│ ...                                     │
└─────────────────────────────────────────┘

GBO[0] 永远是 FileDescriptor：

message FileDescriptor {
  Schema schema = 1;
  uint64 length = 2;    // 文件总行数
}

message Schema {
  repeated lance.file.Field fields = 1;
  map<string, bytes> metadata = 5;
}

这是文件格式唯一的“类型信息”来源：

  • 文件容器本身没有类型概念；
  • 列只是 column index，buffer 只是 global buffer index；
  • 类型、nullable、嵌套结构、field id，全在 GBO[0] 里。

Column Metadata #

Column Metadata数据用于存储每列的元数据，每列对应一个独立的protobuf：

message ColumnMetadata {
  Encoding encoding = 1;        // 列级包装（字典 / 统计）
  repeated Page pages = 2;

  message Page {
    repeated uint64 buffer_offsets = 1;   
    repeated uint64 buffer_sizes   = 2;
    uint64 length                  = 3;   // 页行数
    Encoding encoding              = 4;   // PageLayout
    uint64 priority                = 5;   // 页首顶层行号
  }

  repeated uint64 buffer_offsets = 3;     // 列级 buffer
  repeated uint64 buffer_sizes   = 4;
}

可以看到在每个ColumnMetadata中，有若干个Page组成的页面数组，每个Page的重点字段有：

  • buffer_offsets和buffer_sizes：表示这个数据页面在整个文件中的位置和偏移量
  • length：该页面中存储了多少行数据
  • encoding：页面编码布局，后面将展开讨论

CMO Table #

紧跟在Column Metadata之后，是CMO表，用于存储Column Metadata信息，按照这里给出的(position, size)二元组来解析ColumnMetadata proto 结构体。

(position u64, size u64) × num_columns
共 16 × num_columns 字节

GBO Table #

与 CMO 同构：

(position u64, size u64) × num_global_buffers
  • GBO[0] 是 schema；
  • GBO[1..] 是 add_global_buffer 挂载的任意字节块（索引文件里的 IVF 元数据、zone map 等）。

Footer #

最后是定长的Footer，用于存放整个文件的元数据：

相对末尾偏移 大小 字段
−40 8 column_meta_start
−32 8 column_meta_offsets_start
−24 8 global_buff_offsets_start
−16 4 num_global_buffers
−12 4 num_columns
−8 2 major_version
−6 2 minor_version
−4 4 "LANC"
  • 全部小端无符号；
  • 定长 40 字节，不是 protobuf；

文件结构小结 #

我们已经分析了数据文件的结构，以下是对各组成部分的小结：

区域 大小 定长
Data Region 取决于数据 否
Global Buffer 0 protobuf 序列化长度 否
Column Metadata 每列一段 protobuf 否
CMO 16 × num_columns 是
GBO 16 × num_global_buffers 是
Footer 40 是

根据这个结构，解析数据文件的伪代码如下：

footer = parse_footer(tail[-40:])
gbo    = parse_table(tail, footer.global_buff_offsets_start, footer.num_global_buffers)
schema = FileDescriptor::decode(read(gbo[0].pos, gbo[0].size))
cmo    = parse_table(tail, footer.column_meta_offsets_start, footer.num_columns)
for i in projected_columns:
    col_meta[i] = ColumnMetadata::decode(read(cmo[i].pos, cmo[i].size))

区间公式如下：

[0,                          column_meta_start)         → Data Region
[column_meta_start,         column_meta_offsets_start)  → Column Metadatas
[column_meta_offsets_start, global_buff_offsets_start)  → CMO   (16B × N)
[global_buff_offsets_start, file_len - 40)              → GBO   (16B × GN)
[file_len - 40,             file_len)                   → Footer
