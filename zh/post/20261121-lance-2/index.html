在上篇文章中，分析了 Lance 中各类文件的组织与作用，本篇详细分析其中的数据文件结构（也就是 .lance 后缀的文件），并和 Parquet 做一个对比。需要说明的是，本篇文章会提及Lance的页内编码（如Miniblock、Fullzip等），这部分的详细内容会在后面的文章展开解释。

Lance 数据文件结构 #

如下所示，一个数据文件通常分为以下几大部分：

  • 存放列数据的数据页面
  • Global Buffer（简称 GB），存放不属于任何页、任何列的文件级数据
  • 存储列元数据的 Column Metadata 数组
  • Column Metadata Offset Table（简称 CMO），存储各 Column Metadata 的位置和大小
  • Global Buffers Offset Table（简称 GBO），存储各 Global Buffer 的位置和大小
  • 最后是固定长度的 Footer
┌──────────────────────────────────────────┐
│ Data Pages                               │  ← 各列的数据页
│   （GB[1..] 可能穿插其中）                │
│   Data Buffer 0*                         │
│   ...                                    │
│   Data Buffer BN*                        │
├──────────────────────────────────────────┤
│ Global Buffer 0: FileDescriptor          │  ← GB[0]（含 schema），变长
├──────────────────────────────────────────┤◀── column_meta_start
│ Column Metadatas                         │  ← 每列一个独立 protobuf
│   Column 0 Metadata                      │
│   ...                                    │
│   Column CN Metadata                     │
├──────────────────────────────────────────┤◀── column_meta_offsets_start
│ Column Metadata Offset Table (CMO)       │  ← 16B × CN
├──────────────────────────────────────────┤◀── global_buff_offsets_start
│ Global Buffers Offset Table (GBO)        │  ← 16B × GN
├──────────────────────────────────────────┤◀── file_len - 40
│ Footer (fixed 40 bytes)                  │
│   u64: column_meta_start                 │
│   u64: column_meta_offsets_start         │
│   u64: global_buff_offsets_start         │
│   u32: number of global buffers          │
│   u32: number of columns                 │
│   u16: major version                     │
│   u16: minor version                     │
│   "LANC"                                 │
└──────────────────────────────────────────┘

GB[1..] 是在编码过程中通过 add_global_buffer 就地写入的，因此可能落在数据页之间；GB[0] 则在所有页写完之后、列元数据之前写入，位置固定。

以下对这几部分进行解释。

数据页面 #

从文件偏移 0 开始是数据页面，页内每个 buffer 按 64B 对齐：

文件偏移 0
┌──────────────────────────────────────────┐
│ page 0 ─ buffer 0   [64B 对齐]            │
│          buffer 1   [64B 对齐]            │
│          ...                             │
│ page 1 ─ ...                             │
│                                          │
└──────────────────────────────────────────┘

页本身不要求对齐，对齐的是页内的各个 buffer（不足处补 padding）。数据页面存放具体的列数据，根据列的类型和编码方式会有不同的页内布局，这部分留到后续文章展开。

Global Buffers #

Global Buffers 保存的是不属于任何页、不属于任何列的“文件级”辅助数据，比如 schema、文件级索引、列统计。之所以单独开一块而不是塞进列元数据，是因为容器要对扩展保持中立：索引和统计没有列号，也不该为了放它们而虚构一列。

它只有一条硬规则：

  • GB[0] 恒为 FileDescriptor（schema + 行数）
  • GB[1..] 是任意字节，语义靠 Schema.metadata 的 key → "index[:参数]" 引用

GBO 表里每项 16 字节，记录各 Global Buffer 的位置和长度：

GBO[i] = (GB[i].position, GB[i].size)

GBO（16B × num_global_buffers）
┌────────────────────┬────────────────────┐
│ position u64       │ size u64           │ → GB[0]
├────────────────────┼────────────────────┤
│ position u64       │ size u64           │ → GB[1]
├────────────────────┼────────────────────┤
│ ...                                     │
└─────────────────────────────────────────┘

GB[0] 永远是 FileDescriptor：

message FileDescriptor {
  Schema schema = 1;
  uint64 length = 2;    // 文件总行数
}

message Schema {
  repeated lance.file.Field fields = 1;
  map<string, bytes> metadata = 5;
}

这是文件格式唯一的“类型信息”来源：

  • 文件容器本身没有类型概念；
  • 列只是 column index，buffer 只是 global buffer index；
  • 类型、nullable、嵌套结构、field id，全在 GB[0] 里。

Column Metadata #

Column Metadata 存储每列的元数据，每列对应一个独立的 protobuf：

message ColumnMetadata {
  Encoding encoding = 1;        // 列级 buffer 的解释方式；结构编码下通常为空
  repeated Page pages = 2;

  message Page {
    repeated uint64 buffer_offsets = 1;
    repeated uint64 buffer_sizes   = 2;
    uint64 length                  = 3;   // 页行数
    Encoding encoding              = 4;   // PageLayout
    uint64 priority                = 5;   // 页首顶层行号
  }

  repeated uint64 buffer_offsets = 3;     // 列级 buffer
  repeated uint64 buffer_sizes   = 4;
}

可以看到每个 ColumnMetadata 里有一个由若干 Page 组成的数组，每个 Page 的重点字段有：

  • buffer_offsets 和 buffer_sizes：该页各 buffer 在文件中的绝对偏移与长度
  • length：该页存储了多少行
  • encoding：页布局与编码方式，决定了页内如何组织 buffer
  • priority：该页第一行的行号

CMO Table #

紧跟 Column Metadata 之后是 CMO 表，它记录每个 ColumnMetadata 的 (position, size)，据此解析对应的 protobuf：

(position u64, size u64) × num_columns
共 16 × num_columns 字节

GBO Table #

与 CMO 同构：

(position u64, size u64) × num_global_buffers
  • GBO[0] 指向 GB[0]（FileDescriptor）；
  • GBO[1..] 指向通过 add_global_buffer 挂载的任意字节块（索引文件里的 IVF 元数据、zone map 等）。

Footer #

最后是定长的 Footer，用于存放整个文件的元数据：

相对末尾偏移 大小 字段
−40 8 column_meta_start
−32 8 column_meta_offsets_start
−24 8 global_buff_offsets_start
−16 4 num_global_buffers
−12 4 num_columns
−8 2 major_version
−6 2 minor_version
−4 4 "LANC"
  • 全部小端无符号；
  • 定长 40 字节，不是 protobuf；
  • 放尾部而不是头部，是因为写入时只有把所有页和元数据都写完之后，才知道各区域的偏移；代价是读文件必须先 seek 到末尾 40 字节。

CMO 和 GBO 都是 (position, size) 而不是只有 position，因为每一项都是变长的 protobuf 或任意字节块，长度无法从位置推出。

文件结构小结 #

我们已经分析了数据文件的结构，以下是对各组成部分的小结：

区域 大小 定长
Data Pages 取决于数据 否
GB[0]（schema） protobuf 序列化长度 否
Column Metadata 每列一段 protobuf 否
CMO 16 × num_columns 是
GBO 16 × num_global_buffers 是
Footer 40 是

根据这个结构，解析数据文件的伪代码如下：

footer = parse_footer(tail[-40:])
gbo    = parse_table(tail, footer.global_buff_offsets_start, footer.num_global_buffers)
schema = FileDescriptor::decode(read(gbo[0].pos, gbo[0].size))
cmo    = parse_table(tail, footer.column_meta_offsets_start, footer.num_columns)
for i in projected_columns:
    col_meta[i] = ColumnMetadata::decode(read(cmo[i].pos, cmo[i].size))

用 GB[0] 的偏移可以把文件切成几个区间：

[0,                     GB[0].pos)                       → Data Pages
[GB[0].pos,             GB[0].pos + GB[0].size)          → GB[0]（FileDescriptor）
[column_meta_start,     column_meta_offsets_start)       → Column Metadatas
[column_meta_offsets_start, global_buff_offsets_start)   → CMO   (16B × N)
[global_buff_offsets_start, file_len - 40)               → GBO   (16B × GN)
[file_len - 40,         file_len)                        → Footer

注意 GB[0].pos + GB[0].size == column_meta_start：GB[0] 紧贴在列元数据之前。但 GB[1..] 是就地写入的，可能落在 [0, GB[0].pos) 里，所以「Data Pages」这个区间实际也包含它们。

Parquet 文件结构 #

上面介绍了 Lance 数据文件的结构，接下来对比 Lance 相对 Parquet 做的优化。在此之前，先简略看看 Parquet 的文件结构，了解它的优缺点。

Parquet 的数据文件布局大体如下：

我们可以看到：

  • 一个 Parquet 文件由多个 row group 组成。
  • 每个 row group 中包含多列的数据。
  • 每列的数据又由多个页面组成。
  • 在这些组成部分中，row group 和列数据都是逻辑组件，真正存放数据的物理单元是页面。每个页面前面有一个 PageHeader（Thrift），记录该页的类型、编码方式、压缩前后大小等；schema 和文件版本不在这里，而在文件尾部的 FileMetaData 中。

在 Parquet 中，数据页面是压缩边界，每个页面可以独立编解码，因此 Parquet 可以在页面中采用压缩率更高的“非透明编码”。

这里有必要说明和对比一下“透明编码（transparent encoding）”和“非透明编码（opaque encoding）”。

透明编码和非透明编码 #

所谓透明编码（transparent encoding）：压缩后的数据仍然1:1 逐值可定位。它有以下的特点：

  • 压缩后仍是定宽（或定宽偏移），位置可由 i 直接算出
  • 不跨值依赖（value[i] 不依赖 value[i-1]）
  • 不共享可变状态（不靠“扫描历史”还原）

也就是说，读端能直接算出“第 i 个值在压缩后的位置”，并单独解出这一个值。这个区别对随机访问影响很大：不透明编码要取第 i 个值，必须先把前面 0..i 的数据顺序解出来。两者的对比如下：

  • 透明： value[i] 的位置 = 已知公式 → 单值解码 → 不碰其他值
  • 不透明：value[i] 的位置 = 必须先解出 [0..i) → 串行

常见编码的透明性总结如下：

编码 定宽？ 跨值依赖？ 结论
Flat 是 否 ✅ 透明
Variable（offsets + data） offsets 定宽 否 ✅ 透明
固定位宽 Bitpacking 是 否 ✅ 透明
FSST 是（定宽 code + symbol table） 否 ✅ 透明
Constant 0 字节 否 ✅ 透明
ByteStreamSplit 是（字节流拆分） 否 ✅ 透明（但常接整块压缩）
RLE 否（run 长度变长） 是 ❌
Delta 否 是 ❌
整块通用压缩（zstd / snappy / lz4） 否 是 ❌

下面挑几个展开说明：

RLE 为什么不透明

编码：[(value=7, run=1000), (value=3, run=1), ...]

要取第 1001 个值：

必须先走完第一个 run
→ 才知道第二个 run 在哪
→ 位置不可计算，只能“扫”出来

Delta 为什么不透明

v[0] = base
v[i] = v[i-1] + delta_i

取 v[1000] → 必须从 v[0] 累加 1000 次

ByteStreamSplit 为什么本身是透明的

f32 按字节拆成 4 个流
取 v[i] 只需在 4 个流里各 jump 到第 i 个字节

它在 Parquet 里之所以经常被归到“不透明”一侧，不是因为拆分本身，而是因为它总是再接一层整块通用压缩——一旦套上 zstd，就退化成下面这种不可定位的形态。

整块 zstd / snappy 为什么不透明

压缩块 = [字面量][回溯引用][字面量][回溯引用]...

要解第 i 个字节，必须从块头开始顺序执行所有回溯复制

注意是“整块压缩”不透明。如果每个值单独压一帧（per-value），第 i 个值的位置依然可算——Lance 处理超长值时就是这么做的。

Bitpacking 为什么反而透明

1024 个值，每个 13 bit
byte_offset(i) = i * 13 / 8

只要每块位宽固定，单值定位就成立。

FSST 为什么透明

FSST = 符号表 + 定宽 code 流
每 8 个原始字节 → 8 个 code（1 字节一个）

code 的位置可算，查符号表即可，所以透明。

透明性的代价：

透明 不透明
单值定位 O(1) O(i) 或整块解
压缩率 低 高
可用编码 flat / variable / bitpack / fsst / per-value general + rle / delta / block zstd

回到 Parquet：由于数据页面是压缩边界，Parquet 可以选择压缩比更大的非透明编码，代价是放弃了“单值可定位”——随机访问时必须先把整页解开。

为顺序扫描优化 #

以下是几个典型的顺序扫描的例子：

例 1：数仓聚合报表

SELECT region, sum(amount), count(*)
FROM sales
WHERE ts >= '2026-01-01'
GROUP BY region;

例 2：特征工程 / 训练集导出

tbl = pq.ParquetDataset("s3://bucket/features")
df = tbl.to_table(columns=["user_id", "embedding", "ctr"])
df.write_parquet("s3://bucket/export")

例 3：全表校验 / 统计

SELECT count(*), min(ts), max(ts), count(distinct user_id) FROM events;

以上几个例子的共同点：

  • 结果很小（聚合结果 / 几列）
  • 输入很大（全表或全分区）
  • 扫描比例 > 10%，通常接近 100%
  • 不关心“第 3 行在哪”，只关心“全部扫一遍要多久”

最后一点是决定性的：行与行之间的顺序不重要，只有总字节数重要。

顺序扫描（full scan / column scan） 指：

  • 按顺序、成块地读完整列（或一整个行区间），
  • 在读取的过程中逐行判断条件，
  • 不事先知道“哪些行会命中”。

Parquet 为顺序扫描（尤其是分析型全表/大范围扫描）做的优化，可以从「存储布局」「编码压缩」「元数据跳过」三条线来看。

存储布局：让磁盘 I/O 尽量连续 #

行列混合布局（Row Group + Column Chunk）

文件按 Row Group 水平切分（parquet-mr 默认 128MB，生产上常见调到 512MB～1GB），Row Group 内部按列存储，每列是一个连续的 Column Chunk。这意味着：

  • 扫描某几列时，读的是文件中连续的大块数据，而不是像行存那样读一行、跳过不需要的字段。机械盘时代减少寻道，SSD/对象存储时代则天然匹配预读和大块 GET。
  • Row Group 足够大，一次顺序读的粒度大，摊薄了 open/seek/请求次数，这对 HDFS、S3 这类高延迟存储尤其关键。
  • 列裁剪（projection pushdown）下，不需要的 Column Chunk 完全不读。

页式组织（Page）

Column Chunk 内再切成约 1MB 的 Page，Page 是编码和压缩的最小单元。解码器可以按页流水线式地解压、解码，内存占用可控，也便于 reader 做跨页预读和 I/O 合并（Arrow、Parquet-MR 等实现都有 coalescing 优化，把多个小的逻辑读合并成大块顺序读）。

编码与压缩：减少字节量 + 适配向量化 #

顺序扫描的瓶颈通常是 I/O 带宽，所以 Parquet 在编码上尽量把数据压小、压得“扫描友好”：

  • 字典编码：低基数字段（如状态、枚举）存成字典 + 整数下标，扫描时很多过滤甚至可以直接在字典上做。
  • RLE / Bit-packing：重复值和整数下标用游程 + 紧凑位宽存储，对有序或低区分度列压缩率极高，解码天然适合批量/向量化（SIMD）展开。
  • Delta 编码：时间戳、自增 ID 这类递增序列只存差值。
  • 块压缩（Snappy/Zstd/LZ4）：在 Page 级压缩，换来的是扫描时更少的磁盘字节。Snappy 这种轻压缩选型本身就是“为吞吐让路”的取舍——CPU 解码开销远低于省下的 I/O。

整体效果是：顺序扫描读的字节数可能只有原始数据的 1/5 甚至更少。

元数据：扫描时“该跳就跳” #

顺序扫描不等于必须读完所有字节，Parquet 用分层统计信息支持跳过：

  • Footer：文件末尾的 Thrift 元数据记录了所有 Row Group 的列统计（min/max/null_count、总字节数、编码等）。reader 只需一次尾部 seek 读完 footer，就能规划整个扫描——哪些 Row Group 被谓词排除、要读哪些 Column Chunk、偏移量在哪。
  • Column Index / Offset Index（parquet-format 2.5 引入，parquet-mr 1.11 起支持）：把统计细化到 Page 级，配合 Page 偏移表可以跳过单个数据页，对排序后的数据效果极好（比如按时间排序后扫某个时间窗）。
  • 谓词下推的执行形态：先读过滤列的页、用它把候选行区间裁掉，再对投影列做延迟物化（late materialization），避免把整行读出来再丢弃。

小结 #

层面 设计 对顺序扫描的收益
布局 列式 + 大 Row Group + 连续 Column Chunk 连续大块 I/O，列裁剪
页 ~1MB Page，解码/压缩单元 流式解码，I/O 合并
编码 字典、RLE/Bit-packing、Delta 字节量小，向量化解码
压缩 Page 级 Snappy/Zstd 降低 I/O 带宽消耗
元数据 Footer 统计、Column/Offset Index Row Group/Page 级跳过

核心思想一句话：牺牲细粒度随机访问的能力，换取“读的就是要用的、读的过程全是大块连续 I/O、能不读的通过统计跳过”。这也是为什么 Parquet 适合 OLAP 扫描，而点查型负载需要额外的索引或行存层。

例子 #

假设一张表：

10 亿行 × 20 列 ≈ 200 GB（逻辑，未压缩）

查询：

SELECT region, sum(amount) FROM sales
WHERE ts >= '2026-01-01' GROUP BY region

列存先砍一刀

20 列 → 只读 3 列（region / amount / ts）
假设这 3 列占 30 B/行
→ 30 GB 逻辑

6.7x 缩减，这一步由列存完成，和 row group 无关。

压缩再砍一刀

同质数据（region 低基数、amount 有分布、ts 单调）
+ delta / RLE / dictionary / zstd
→ 约 4x
→ 30 GB → 7.5 GB 物理

row group 统计再跳一点

1 GB row group → 200 个
每个 row group 在 ts 上记录 min/max → 跳过 30% 不可能命中的 row group
→ 5.25 GB 物理

合计：

200 GB 原始
→ 30 GB（列裁剪）
→ 7.5 GB（压缩）
→ 5.25 GB（统计跳过）
总缩减 38x

以 Parquet 的文件结构，顺序扫描的大致流程如下：

1. 读尾部 8 字节 → footer length + magic
2. 读 FileMetaData（可能几 MB）
3. 对每个未剪枝的 row group、每列：
     read dictionary page（如果有）
     read data pages（顺序）
     解压、解码
4. 拼 batch

较差的点查性能 #

然而，Parquet 的设计对点查却不太友好。例如这样的点查查询：

SELECT * FROM sales WHERE id = 12345678;

对 Parquet 文件的访问路径变成：

1. 读 footer（几 MB）
2. 读 3 个 column chunk 的元数据
3. 读 dictionary page
4. 定位到 1 个 page（1 MB）
5. 解压整页
6. 解 levels 走到那一行
7. 取 200 B

读了 ~1 MB，拿到 200 B
读放大 5000x

究其根本原因，Parquet 的文件设计是为优化顺序扫描而设计的。顺序扫描的账只有两项：总字节数、请求数。Parquet 的每个设计都在压这两项：

  • 列存 → 少读列
  • 1 MB 页 → 少发请求
  • 非透明编码 + 大块压缩 → 少读字节
  • 统计剪枝 → 再少读一点

代价是“页内不可定位”，但只要命中比例高，这个代价就被摊薄到可以忽略。

为什么 Lance 需要随机访问 #

Parquet 能接受这个代价，是因为它的主场景是分析型扫描：一条查询动辄扫过百万行，单次点查的读放大被整体吞吐摊薄。Lance 面对的工作负载不是这一种。

索引回表 #

向量检索、全文检索、标量索引有共同形态：先用索引拿到一批行地址，再按地址回表取出原始数据。

query → 索引 → [row_addr, row_addr, ...] → 回表 → 结果

top-k 通常只有几十到几百行，却散布在整个文件甚至多个 fragment 里。这一步天然是随机的，而且它是索引查询的必经路径——索引构建得再快，回表慢就等于全文检索、向量检索整体慢。

行地址本身也是为这件事设计的：

row_address = (fragment_id << 32) | local_row_offset

给定地址，位运算就能拆出 fragment 和行偏移，不需要任何查找表。

训练时的随机采样 #

机器学习训练要把数据集打散成 batch：

一个 epoch：N 个 batch，每个 batch 随机取 B 行
每一行可能来自不同 fragment、不同页

打散不是可选优化。batch 内样本若有相关性，梯度质量会受影响，所以随机性属于训练语义的一部分。如果取一行要 1 MB，GPU 就会因为等 I/O 而空转——这也是 Lance 强调高 GPU 利用率的直接原因。

对象存储把读放大变成延迟和账单 #

同样的读放大，在本地磁盘和对象存储上代价完全不同：

本地磁盘 对象存储
多读 1 MB 几毫秒 一次 GET 的固定延迟（几十毫秒）
计费 不计 按请求数 + 流量计费
吞吐 高 单流受限，需靠并发摊薄

取 200 B 却付 1 MB 的流量和延迟，在服务化场景下会直接体现为成本和 P99。尤其是并发几十上百个点查时，读放大是按倍数相乘的。

两类负载的形状不同 # 

分析型扫描：读得多，但连续        → 瓶颈是顺序吞吐
索引回表 / 训练采样：读得少，且散  → 瓶颈是单次请求的字节数

Lance 的目标负载偏后者。顺序扫描当然仍是大多数查询的主体，但只针对顺序扫描优化，索引回表和训练采样就会被文件格式本身卡住——而这两类恰好是 AI 数据栈的核心路径。

于是问题变成一个必须同时满足的约束：

顺序扫描要页足够大（摊薄 I/O 与元数据开销）
随机访问要读取粒度足够小（控制单次请求字节数）

Parquet 用“页”这一个单位同时承担两件事，所以只能折中。Lance 的答案是把它拆成两层——这就是下一节要讲的。

Lance 对比 Parquet 的优化 #

对比 Parquet，Lance 的数据文件格式设计主要有两点变化：

  • 取消 row group，每列独立分页
  • 页内引入可定位结构（MiniBlock / FullZip），让随机访问落到字节区间

以下展开解释。

取消 row group #

row group 是 Parquet 中特有的设计，一个 Parquet 文件被切成多个 row group，每个 row group 内含各列的一段数据。以包含列 id、name、embedding 的表为例，假设把 row group 调到 100 万行，其物理结构如下：

Parquet file
├── RowGroup 0            ← 行方向切一刀：第 0 ~ 999,999 行
│   ├── ColumnChunk: id        （这 100 万行的 id）
│   ├── ColumnChunk: name      （这 100 万行的 name）
│   └── ColumnChunk: embedding （这 100 万行的 embedding）
├── RowGroup 1            ← 第 1,000,000 ~ 1,999,999 行
│   ├── ColumnChunk: id
│   ├── ...
└── ...

在上面的例子中，数据模型大体如下：

RowGroup {
  num_rows: 1_000_000
  columns: [
    ColumnChunk { column: id,        num_values: 1_000_000 },
    ColumnChunk { column: name,      num_values: 1_000_000 },
    ColumnChunk { column: embedding, num_values: 1_000_000 },
  ]
}

这样的设计带来的问题是：RowGroup 在第 1,000,000 行处切开，也就是说，同一个 row group 的所有列必须覆盖完全相同的行区间。

这样的设计造成以下几个问题：

行数被最宽列绑架 #

Parquet 的 row group 按字节控制大小（parquet-mr 默认 128MB），但它覆盖的行数由整行宽度决定，所有列共用这个行数。考虑两列：

  • embedding = fixed_size_list<float32, 1024> = 4096 字节/行
  • id = 8 字节/行

整行约 4.1 KB，所以 128MB 的 row group 只有约 3.2 万行：

embedding chunk = 3.2 万 × 4096B ≈ 128 MB
id        chunk = 3.2 万 × 8B    ≈ 256 KB   ← 窄列只剩个零头

反过来，想让 id 的 chunk 达到 8MB 左右（一页），row group 得放大到 100 万行；此时 embedding 的 chunk 就是 4 GB，写侧要为这一个 row group 缓冲大量数据（不少实现靠溢出落盘来兜底，但代价是写放大）。

也就是说，窄列需要的行数和宽列能承受的行数相差几个数量级，却只能共用一个值。

读放大的下限是“页”，不是 chunk #

这里要区分两个概念：

  • chunk：一列在一个 row group 内的全部数据，大小 = row group 行数 × 该列单行宽度
  • page ：chunk 内部再按字节切出来的块，默认约 1 MB

点查读的是页：定位到目标行所在页，读大约 1 MB，再解压整页。所以读放大倍数 ≈ page_size / row_size，与 chunk 大小无关。页大小在格式层面是按页记录的，并不被 row group 的行数直接卡死（部分实现支持按列配置页大小）。

真正被 row group 绑住的是另外两件事：

  1. 统计剪枝的粒度：footer 里的 min/max 是 row group 级的，要细到页级得额外写 Column Index / Offset Index（可选，不少写入端并不开启）。
  2. 切分与并行：row group 天然是任务划分和文件切分的单位，行数不合适时，窄列全是 runt page、宽列又要吃满内存。

row group 小 → runt page #

反过来，把 row group 调小：

  • 1 万行时 id chunk = 1万 × 8B = 80 KB，1000 行时只有 8 KB；
  • 此时窄列的页可能只有几 KB，这就是所谓的 runt page（发育不良的小页）；
  • 云存储上一次 I/O 有固定开销（延迟、请求计费、吞吐下限），几 KB 的页读起来极不划算，顺序扫描也会退化成海量小请求。

于是陷入两难：

  • row group 小 → 行数少，窄列整个 chunk 只有几十 KB 甚至几 KB，再切页就是 runt page；
  • row group 大 → 想给窄列攒出足够字节，行数就得放大，而宽列的 chunk 按倍数膨胀，写侧要为整组缓冲。

无论怎么调，窄列和宽列的诉求都绑在同一个行数上。

Lance 的做法 #

因为以上的考虑，Lance 取消了 row group，只保留“页”：每列独立分页，每页只存放一列的数据，页的大小按列自己的字节预算计算——写入端默认每列累积约 8 MiB 就切一页（data_cache_bytes 可调），与其他列完全无关。这样 Lance 才能支持部分页读取：

  • 每页记录首行行号（priority），读某段行时先定位到页；
  • 页内编码（MiniBlock / FullZip / Sparse）允许从页面中间开始解码；
  • 元数据给出精确的 buffer offset/size，可以只发一个 range GET。

优化随机访问 #

Lance 的随机访问能力建立在「页内可定位」上。先看取消 row group 在这里起的作用，再看页内的几个机制。

取消 row group：让“页保持大”和“点查读得少”不再互斥 #

点查读的从来不是整个 chunk，而是页：在列元数据里按行号定位到页，读大约一个页的字节，再解压。chunk 有多大，不影响这一次读取的字节数。

真正决定点查读取量的是页大小。而在 Parquet 里，页同时是编码单元、压缩单元和 I/O 单元，三者绑死：

Parquet：点查最小读取量 = 页大小
        想让点查读得少 → 页必须小
        页一小 → 压缩窗口变小、页头占比升高 → 顺序扫描变差
        于是只能折中，典型取 1 MB

也就是说，Parquet 的点查放大下限被“压缩率”钉在 1 MB 这一级；想再往下压，顺序扫描就要付代价。

而 row group 让这条约束更难绕开。chunk 大小 = 行数 × 该列单行宽度，同一 row group 里各列的行数完全相同，于是窄列的 chunk 可能只有宽列的几百分之一：

128 MB row group ≈ 3.2 万行
→ embedding chunk ≈ 128 MB，id chunk ≈ 256 KB
→ 页大小不能超过 chunk 大小：窄列连 1 MB 的页都放不下
→ 想让窄列也能用大页，只能给 row group 塞更多行
→ 宽列的 chunk 按同样倍数一起膨胀

也就是说，页大小这个本来该按列单独决定的参数，被迫在“整组行数”这一个数字上妥协。

Lance 取消 row group 之后，页的大小可以纯粹按 I/O 经济性、并且按列单独来定，点查粒度不再等于页大小：

Lance：页  ≈ 8 MB      → 顺序扫描摊薄 I/O 与元数据开销
       块  ≈ 4 KB     → 点查只读命中的 chunk

页大不影响点查读得少，块的压缩窗口也不至于小到伤压缩率。取消 row group 在这里的作用，是解除“页大小必须同时服务随机访问”这条约束。

副产品是每列的页数完全独立（列 A 3 个页、列 B 17 个页、列 C 1 个页），窄列不必为了迁就宽列被挤成 runt 页，宽列也不必为了迁就窄列被限制大小。

把点查读取量从 1 MB 压到 4 KB 的是下一节的块索引；取消 row group 让“大页 + 小块”能同时成立。两者叠加，才有后面那张点查对比里的数字。

Page.priority 把“行→页”变成二分 # 

message Page {
  uint64 length = 3;
  uint64 priority = 5;   // 这一页第一行的行号
}

页表天然按 priority 有序，partition_point 一次二分就能找到相交的页。

Parquet 要么靠可选的 OffsetIndex，要么从头扫变长的 Thrift 页头。

页内再拆 chunk：buffer 0 #

MiniBlock 页把“索引”和“数据”放在不同的 buffer 里（有字典或 list 时还会多出字典、rep index 等 buffer）：

buffer 0  每 chunk 一个 2–4 字节的索引字
buffer 1  所有 chunk 首尾相接

索引字里编码了两件事：这个 chunk 占多少个 8 字节字，以及块内有多少个值（以 log2 表示）：

word = ((chunk_bytes / 8 - 1) << 4) | log2(num_values)

读端在初始化时把 buffer 0 整体载入内存（每个 chunk 只占 2–4 字节），前缀和算出第 r 行落在第 k 个 chunk，再用 chunk_bytes 得到它在 buffer 1 里的精确字节区间——随机访问时只需读那一个 chunk。

而 Parquet 的页是一个不可切分的压缩块，页内没有任何定位结构。

MiniBlock 的 buffer 布局（索引、rep/def、值分开存放）和块头的具体格式，这里不展开。

压缩编码的选择被“可定位性”约束 #

  • Parquet：可以 delta / RLE / BSS / 整块 zstd 等非透明压缩，压缩率高，代价是每次都必须把整个页解开。
  • Lance：MiniBlock 是块级压缩，chunk 内仍可用 RLE / BSS / zstd；但 FullZip（值级交错布局）强制逐值透明，压缩后必须还能算出第 i 个值的位置。

因此 Lance 的 FullZip 压缩率通常偏低，补偿手段是“单值 ≥ 32 KiB 时逐值 zstd”——逐值压一帧，位置依然可算。

删除走位图，不重写 #

这一条已经超出单个数据文件的范围，属于数据集层的设计，但它直接决定了“删一行要付多少代价”：

  • Parquet 格式本身没有删除语义，删一行要靠引擎读-改-写整个 row group（跨列）。
  • Lance 用 _deletions/ 下的位图记录被删除的行，数据文件本身不动。删一行的代价从重写整个 row group 降到写一个小文件。

元数据可以按列取 #

  • Parquet：所有元数据集中在 Footer 里，打开文件要一次读完，大小 O(row_groups × columns)。
  • Lance：元数据分散在 CMO / GBO 中，每列 16 字节，只读投影列的元数据，宽表 + 窄投影时打开文件的成本差距明显。

一次点查的对照 #

根据 Parquet 和 Lance 的数据文件结构，一次点查的流程对比如下：

Parquet：
  读 footer（几 MB）
  → 定位 row group
  → 读 dictionary page
  → 扫页头或查 OffsetIndex
  → 读 1 MB 页
  → 解压整页
  → 解 levels 走到目标行
  → 取 200 B          读放大 ≈ 5000x

Lance：
  查 manifest 得 fragment → file（0 I/O）
  → Page.priority 二分（内存）
  → 查 buffer 0（初始化时已进缓存）
  → 读命中 chunk（约 4 KiB）
  取 200 B            读放大 ≈ 20x

Lance 的读放大并没有消失，只是从“整页 1 MB”缩到了“一个 chunk 4 KiB”这一级。真正需要担心的是 chunk 别做得太大，这也是 MiniBlock 把块压到 32 KiB 以内的原因。

两者的特点是：

  • Parquet 的随机访问是“先定位到页，再把页整个解开”；
  • Lance 的随机访问是“逐层定位到字节区间，只读命中的那一小块”。

代价 #

Lance 不是“更优”，而是“换了一种代价”：

代价 说明
压缩率偏低 FullZip 必须透明，不能用 delta / 整块 zstd
元数据更复杂 CMO / GBO / PageInfo / ChunkIndex / rep index 多层
调度更复杂 需要自己的 FieldScheduler / PageScheduler
顺序扫描略慢 解压粒度碎（4 KiB vs 1 MB），大块 SIMD 机会少
额外文件类型 _deletions/、_indices/

小结 #

把两边的结构放在一起看，差异只有一句话：

  • Parquet：row group → column chunk → page（页内不可定位）
  • Lance ：column → page → buffer（页内可定位到 chunk）

Lance 去掉了跨列共享的 row group，让每列按自己的字节预算分页；再在页内用 buffer 0 的块索引把随机访问落到具体字节区间。

两边是两种取舍，没有绝对优劣：

  • Parquet 用读放大换压缩率和顺序吞吐；
  • Lance 用元数据复杂度和压缩率换随机访问的字节数。

粗略的判据是命中比例：

命中 > 5%–10%  → 顺序扫描，Parquet 更优
命中 < 1%      → 随机访问，Lance 更优

页内的三种布局（MiniBlock、FullZip、Sparse）细节较多，会在后续文章中单独展开。
